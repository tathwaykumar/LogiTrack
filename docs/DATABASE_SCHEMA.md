# Database Schema Reference

This document describes the PostgreSQL schema that LogiTrack actually runs on. Everything here was taken
from a database built from the repository files exactly as described in [SETUP.md](SETUP.md):
`database/schema.sql` followed by the seven migration files in `database/migrations/` (001–007). A database built this way has 24 tables, 36 foreign keys, 26 CHECK constraints and 50 indexes (counted from the PostgreSQL catalogue). Column types, constraints, indexes and
triggers were read back from PostgreSQL's catalogue, not inferred from names.

- Entity-relationship diagram: [ER_DIAGRAM.md](ER_DIAGRAM.md)
- How the application uses these tables: [ARCHITECTURE.md](ARCHITECTURE.md)

## 1. Where the schema comes from

| Source | What it creates |
|---|---|
| `database/schema.sql` | A `pg_dump` (PostgreSQL 18.6, dated 2026-09-03) containing 20 tables, the `shipment_summary` view, the `calculate_order_total` function, the `update_shipment_status` trigger function and procedure, and the `trg_update_shipment_status` trigger. |
| `database/migrations/001_order_inventory_reservation.sql` | Table `order_inventory_reservation` and its indexes. |
| `database/migrations/002_shipment_one_active_per_order.sql` | Partial unique index `uq_shipment_order_active`. |
| `database/migrations/003_status_transition_rules.sql` | Status-rule functions and triggers; replaces the body of the `update_shipment_status()` trigger function; reconciles inconsistent `delivery` rows. |
| `database/migrations/004_shipment_item_same_order.sql` | Unique constraint `uq_shipment_id_order` on `shipment` and composite foreign key `fk_shipment_item_shipment_order` on `shipment_item`. |
| `database/migrations/005_order_fulfilment_planning.sql` | Tables `order_fulfilment` and `order_fulfilment_event`; columns `delivery.vehicle_id`, `delivery.assigned_at`, `orders.destination_city`, `order_inventory_reservation.released_at`; their indexes and foreign keys; trigger `trg_sync_order_with_shipment`. Adds only; changes no existing row. |
| `database/migrations/006_operations_approval_and_demo_ledger.sql` | Columns `order_fulfilment.approved_at` and `approved_by_user_id` (with `fk_fulfilment_approved_by`); table `demo_seed_record`. Existing orders are not marked approved. |
| `database/migrations/007_shipment_route_optional.sql` | `shipment.route_id` becomes nullable (`DROP NOT NULL`); the foreign key stays. Changes no row. |
| `database/seed.sql` | Sample data (not schema). Runs in one transaction, loads the historical shipment rows exactly as written, and advances every ID sequence. Works before or after the migrations. |
| `backend/models.py` | SQLAlchemy models used by the API. They mirror the tables above, and a test fails if they drift. **The models do not create tables** (there is no `create_all` call). See [section 7](#7-the-models-and-the-database). |

There is no migration tool (such as Alembic) and no table that records which migrations have run. Migrations are
plain SQL files applied in filename order; each one is written to be safe to re-run.

## 2. Conventions

- All tables are in the `public` schema.
- `serial` means an `integer` column whose default is `nextval(<table>_<column>_seq)`.
  `order_inventory_reservation.reservation_id` is the one `GENERATED BY DEFAULT AS IDENTITY` column.
- `timestamp` means `timestamp without time zone`. `varchar(n)` means `character varying(n)`.
- No foreign key declares an `ON DELETE` or `ON UPDATE` action, so all use PostgreSQL's default `NO ACTION`.
  A referenced row cannot be deleted while rows still reference it.
- Status columns are `varchar` columns restricted by a `CHECK` constraint where one exists. Several status
  columns (for example `vehicle.status`, `driver.availability_status`, `warehouse.status`, `route.route_status`,
  `employee.employment_status`, `invoice.invoice_status`) have **no** CHECK constraint and accept any string.

| Column | Type | Null | Default | Notes |

## 5. Database-enforced business rules

### 5.1 Order inventory reservation (migration 001 + checkout code)

What the **database** guarantees:
- A reservation always refers to an existing order line (`fk_reservation_order_item`).
- At most one reservation row per order, warehouse and product (`uq_reservation_order_warehouse_product`).
- Reserved quantities are positive; stock can never go negative (`chk_inventory_quantity`).

What the **application** does (`POST /shop/checkout`, `backend/main.py`):
- It locks the product and inventory rows (`SELECT … FOR UPDATE`), takes stock from warehouses in ascending
  `warehouse_id` order, **deducts it from `inventory.quantity` immediately**, and writes one reservation row
  per warehouse used, all in the same transaction. A failed checkout rolls back both.
- "Reservation" here therefore means *the recorded source of stock already deducted*, not a separate held
  quantity. There is no reserved-quantity column on `inventory`: reserved units are the active reservation rows
  (`released_at IS NULL`) of orders that have not been picked up, available units are `inventory.quantity`, and on hand is
  the two together.
- Since migration 005 an unpaid order that is cancelled (`POST /orders/{id}/cancel`) or abandoned
  (`POST /operations/release-abandoned`) gets its stock back exactly once, marked by `released_at`.
- A paid order that predates reservations can have its stock reserved after the fact with
  `POST /operations/orders/{id}/recover-reservation` (explicit staff confirmation, all-or-nothing, §5.8).
- The database does **not** require reservations to add up to the order quantity. The payment code checks this
  and refuses to approve the order or create a shipment (`RESERVATION_MISSING` / `RESERVATION_INCOMPLETE`) when they do not.

### 5.2 One active shipment per order (migration 002)

`uq_shipment_order_active` is a partial unique index on `shipment(order_id)` covering rows whose
`shipment_status <> 'CANCELLED'`. The consequences are:
- An order can have any number of `CANCELLED` shipments, but at most one shipment in any other status.
- `POST /shipments`, payment fulfilment and status changes all hit the same index. The API maps a violation to HTTP 409.
- Migration 002 refuses to install (raising an error) if existing data already has duplicate non-cancelled shipments.

### 5.3 Shipment and delivery status rules (migration 003)

**Source of truth.** `shipment.shipment_status` is set by inserting `shipment_tracking` events. The
`delivery.delivery_status` is derived from it:

| Shipment status | Compatible delivery status |
|---|---|
| `CREATED`, `PICKED_UP`, `IN_TRANSIT` | `PENDING` |
| `OUT_FOR_DELIVERY` | `OUT_FOR_DELIVERY`, or `FAILED` (failed attempt) |
| `DELIVERED` | `DELIVERED` |
| `CANCELLED` | `CANCELLED` |

**Transitions.**
- Forward only through `CREATED < PICKED_UP < IN_TRANSIT < OUT_FOR_DELIVERY < DELIVERED`. Stages may be skipped.
- An event with the current status is allowed (a location "checkpoint").
- `CANCELLED` can be reached from any open stage.
- `DELIVERED` and `CANCELLED` are terminal: no status change and no new tracking events.

**Enforcement.** Violations raise `SQLSTATE 'LT409'`, which the API turns into HTTP 409. Because the rules live in
triggers, they also apply to direct SQL and to the `update_shipment_status` procedure:

| Trigger | Rule |
|---|---|
| `trg_guard_tracking_event` | Locks the shipment row (`FOR UPDATE`, serialising concurrent events) and rejects any event for a `DELIVERED`/`CANCELLED` shipment. |
| `trg_update_shipment_status` | Copies the event status onto the shipment; turns a `FAILED` delivery back into `OUT_FOR_DELIVERY` on a new attempt. |
| `trg_enforce_shipment_status_transition` | Rejects backward moves and changes to terminal shipments; sets `actual_delivery` when the status becomes `DELIVERED`. |
| `trg_sync_delivery_with_shipment` | Updates the delivery to the compatible status (and copies `actual_delivery` into `delivery_date`). |
| `trg_enforce_delivery_status` | Rejects a delivery status incompatible with its shipment and any change to a `DELIVERED`/`CANCELLED` delivery. |

**One-off data repair.** Migration 003 updates existing `delivery` rows whose status contradicts their shipment
(for example a shipment `DELIVERED` by tracking whose delivery still said `PENDING`). It only derives the status,
and copies `actual_delivery` into `delivery_date` when one exists. It never touches `shipment_tracking`.

### 5.4 Shipment items belong to the shipment's order (migration 004)

`shipment_item` stores `order_id` only so it can reference `order_item (order_id, product_id)`. Before migration 004
nothing stopped that `order_id` differing from `shipment.order_id`. The migration adds
`UNIQUE (shipment_id, order_id)` on `shipment` and the composite foreign key
`shipment_item (shipment_id, order_id) → shipment (shipment_id, order_id)`.

- The unique constraint cannot fail on existing data, because `shipment_id` is already unique.
- The migration first checks existing rows. If any item names a different order than its shipment, it raises an
  error listing the shipment IDs and changes nothing. It is safe to re-run.

### 5.5 Other CHECK constraints

The remaining rules are the CHECK constraints listed per table in §3: non-negative stock, prices and
costs; positive quantities, amounts, distances and capacities; date ordering on assignments and shipments;
`invoice.total_amount = subtotal + tax`; and the allowed values of `orders.order_status`,
`payment.payment_status`, `shipment.shipment_status` and `delivery.delivery_status`.

### 5.6 Payment before approval before dispatch (migration 006 + application)

The database stores the approval (`order_fulfilment.approved_at`, `approved_by_user_id`) and the audit log; the **application** enforces the
order of events: a shipment is created only for an order with a `SUCCESS` payment that is not cancelled, and only after an Operations
Manager approves it (`POST /operations/orders/{id}/approve`) or creates the shipment by hand (`POST /shipments`, which applies the same
payment check and records the approval). Payment alone never creates a shipment. Nothing at the database level prevents an
administrator inserting a shipment with SQL; the rule lives in the API.

### 5.7 Order status follows its shipment (migration 005)

`trg_sync_order_with_shipment` moves `orders.order_status` to `SHIPPED` when its shipment becomes `PICKED_UP`, `IN_TRANSIT` or `OUT_FOR_DELIVERY`, and
to `DELIVERED` when the shipment is delivered. It never moves an order backwards and never touches a cancelled order. It applies to shipment
changes made after the migration; orders that were already out of step are **not** corrected (see
[ER_DIAGRAM.md](ER_DIAGRAM.md#discrepancies-found)).

### 5.8 Routes are optional (migration 007)

`shipment.route_id` and `order_fulfilment.route_id` are nullable. A route is recorded only when exactly one active route runs from the
origin warehouse's city to the order's destination; otherwise the shipment has no route and no estimated delivery. Nothing about
routes can block approval, shipment creation or driver assignment.

### 5.9 Recovering stock for a paid order without a reservation

`recover_missing_reservation()` (`backend/fulfilment.py`) runs in one transaction under a row lock on the order and `FOR UPDATE` locks on the stock:
it requires a `SUCCESS` payment, an uncancelled order without a shipment, no earlier or active reservation, and an explicit confirmation that the
stock was not already deducted; it deducts the stock, writes the reservation rows and a `STOCK_RECOVERED` log entry, and does nothing else.
`inventory.quantity >= 0` (`chk_inventory_quantity`) is the final guard against overselling.

## 6. Design and normalisation

**Keys.** Every entity table has a surrogate integer key. Natural candidate keys are enforced as `UNIQUE`:
`role.role_name`, `users.username`, `users.email`, `driver.license_no`, `vehicle.registration_no`,
`payment.transaction_reference`. One-to-one links are enforced with unique foreign keys: `customer.user_id`,
`employee.user_id`, `payment.order_id`, `invoice.order_id` and `delivery.shipment_id`.

**Associative entities.** Four tables resolve many-to-many relationships:
- `order_item` (orders ↔ product), with a composite primary key.
- `inventory` (warehouse ↔ product), with a composite primary key.
- `driver_vehicle_assignment` (driver ↔ vehicle over time), with a surrogate key.
- `order_inventory_reservation` (order line ↔ warehouse), with a surrogate key and a unique triple.

**Specialisation.** `driver` shares its primary key with `employee` (a 1:1 "is-a" subtype).
`customer` and `employee` are separate profiles hanging off `users`.

**Normal forms.** The claims below assume that the only functional dependencies are the ones implied by
each table's declared primary and unique keys, plus the dependencies called out explicitly. With that assumption:

- **1NF.** All columns hold single values. One caveat: `orders.shipping_address`, `customer.address` and
  `delivery.delivery_address` are single free-text strings. The application treats them as atomic, *except*
  that payment fulfilment searches them for a city name to choose a route. If the city is considered a
  separate fact, the address is a composite attribute.
- **2NF and 3NF.** Tables with single-column keys cannot have partial dependencies. Among composite-key tables:
  - `inventory (warehouse_id, product_id)`: `quantity`, `reorder_level` and `last_updated` depend on the whole key.
  - `order_item (order_id, product_id)`: `quantity` and `unit_price` depend on the whole key. `unit_price` is the
    price *at the time of the order*, deliberately not `product.unit_price`, so it is not determined by
    `product_id` alone. If it were meant to equal the current price, it would be a transitive copy.
  - `shipment_item (shipment_id, product_id)`: **strictly not in 2NF.** `shipment_id → order_id` holds, because each
    shipment belongs to one order, so `order_id` depends on part of the key. It is stored deliberately so the row can
    reference `order_item (order_id, product_id)`. Since migration 004 the redundancy is *controlled*: the composite
    foreign key `fk_shipment_item_shipment_order` forces it to equal `shipment.order_id`, so it cannot disagree with
    the shipment. Removing the column would need a different way to tie items to order lines, which this design
    does not use.
- **BCNF.** For the remaining tables, every determinant is a candidate key under the stated assumption.
  `role`, `users`, `driver` and `vehicle` each have more than one candidate key (surrogate plus a unique natural
  key), and both kinds are enforced.
- **Controlled redundancy (derived data), each kept consistent by a constraint or trigger:**
  - `invoice.total_amount` is derived from `subtotal + tax` (CHECK `chk_invoice_calculation`).
  - `shipment.shipment_status` caches the latest `shipment_tracking.status` (trigger).
  - `delivery.delivery_status` is derived from the shipment status, except `FAILED` (triggers).
  - `shipment_item.order_id` repeats `shipment.order_id` (composite foreign key, migration 004).
- **Snapshots (intentional copies, not kept in sync):** `order_item.unit_price`, `delivery.delivery_address` and
  `shipment.estimated_delivery`.
- **Text matches instead of keys:** `route.source` and `route.destination` are city names compared as text with
  `warehouse.city` and with shipping addresses. There is no foreign key between routes and warehouses.

## 7. The models and the database

`backend/models.py` mirrors this schema: tables, columns and nullability, server-side defaults, foreign keys
(including the composite ones), unique constraints, all 26 CHECK constraints and every index. The test
`backend/tests/test_models_match_schema.py` builds the database from the SQL files and compares it with the
SQLAlchemy metadata table by table, so the two cannot drift apart unnoticed. (Run against the previous version of
`models.py` it fails for 21 of the 22 checks, which is how it was shown to work.)

What the models still do **not** represent, because SQLAlchemy has no equivalent:
- triggers, functions, the stored procedure and the `shipment_summary` view;
- the ordering rules those triggers enforce.

So `Base.metadata.create_all()` would create tables with the right columns and constraints but **without the
status rules or the view**. Always build the database from the SQL files.

**Behaviour fixed by the alignment.** The models used to omit most server defaults, so rows written through the ORM
could get `NULL` where the SQL default would have supplied a value: `users.created_at` for accounts created by
`POST /auth/register`, and `shipment.shipment_date` for shipments created by `POST /shipments`. Both are now
filled by the database.
